# معمارية AGOS v2 — سجل القرار (ADR-001، D-151)

> **الحالة**: معتمد للتنفيذ (R-202، لاحق 154، 2026-11-12). يتبعه كل بند في M10 بعد R-202. أي خروج عنه يحتاج قرار D-NNN جديدًا يعدّل هذا الملف في الدفعة نفسها.
> **المرجع**: هدف المالك (D-150) و[`ROADMAP_V2_AR.md`](roadmaps/agos-v2/ROADMAP_V2_AR.md) §4، وجرد الحقيقة R-200 ([`REPORT_AR.md`](../audit/M10/inventory/REPORT_AR.md)).
> **الملفات المرافقة**: نموذج البيانات [`DATA_MODEL_V2.md`](DATA_MODEL_V2.md)، المخطط [`docs/sql/v2/001_core.sql`](../sql/v2/001_core.sql)، العقود [`contracts/v2/`](contracts/v2/README.md)، الكود `agos_v2/contracts.py`، الاختبار `tests/test_r202_v2_schema.py`.

## 1. السياق

v1 خادم FastAPI حقيقي في ملف واحد (~3500 سطر)، فيه 20 معالجًا حقيقيًا، يوجّه المحادثة بالكلمات المفتاحية إلى معالج واحد. وفيه مخطِّط DAG حقيقي (`/civilization/*`) لا تصل إليه الواجهة. الحالة في الذاكرة (`TASKS`، `CIVILIZATION`)، ولا حسابات ولا مفاتيح للمستخدم (R-200). المطلوب منصة تدير وكلاء حقيقيين وتنسق عملهم، ولا تفقد السياق، وتتحقق من نتائجها وتصحح نفسها أو تعلن الفشل.

## 2. القرار — الطبقات

```
المستخدم ──► web (React)  ──►  web service (FastAPI): /api/v2/* + SSE + الواجهة
                                   │  حسابات Supabase Auth، صلاحيات، حدود معدل، مفاتيح مطورين
                                   ▼
                     Postgres (Supabase) — المخطط agos  ◄── المصدر الوحيد للحالة
                     tasks / steps / task_events / messages / artifacts / memory_items
                                   ▲
                                   │  claim (claim_token + lease) ، كتابة الخطوات والأحداث
                     worker (نفس الكود، دور مختلف): المنسق
                       مخطِّط ← رسم خطوات بمعايير قبول ← وكيل لكل خطوة ← تحقق ← تصحيح محدود ← نتيجة أو فشل معلن
                                   │
                     أدوات + بيئة معزولة + موصلات  ──►  بوابة النماذج (BYOK / مفتاح المنصة)
```

1. **لا حالة في الذاكرة.** كل هدف وخطوة وناتج وحدث يُكتب في Postgres قبل أن يُعتبر حدث. إعادة تشغيل أي عملية لا تفقد شيئًا، والعامل يستأنف من آخر خطوة مكتملة. هذا هو تعريف «لا فقدان سياق» في v2: السياق يُعاد بناؤه من `task_events` و`steps`، لا من نافذة النموذج.
2. **حدود الخدمات**: دوران من نفس الكود: `web` (API، المصادقة، SSE، الواجهة الثابتة) و`worker` (المنسق والوكلاء والأدوات والتحقق). لا يتكلمان إلا عبر قاعدة البيانات. لا تعدد عمال Uvicorn داخل العملية (قاعدة ثابتة).
3. **التشغيل على الخطة المجانية**: Render المجاني لا يوفر Background Worker ([Render: Deploy for Free](https://render.com/docs/free) — الأنواع المجانية: web وPostgres وKey Value فقط). والخدمة المجانية تتوقف بعد 15 دقيقة بلا طلبات؛ عند عودتها يستعيد العامل المهام ذات الـlease المنتهي (آلية R-163)، فلا تضيع مهمة، لكنها تتأخر. لذلك يعمل `worker` في البداية **مضمّنًا** داخل عملية `web` (نفس مسار الكود، المطالبة عبر القاعدة). فصله إلى خدمة مستقلة إعداد فقط، ويحتاج موافقة المالك على التكلفة (R-238). **بيئة free ليست إثبات سعة.**
4. **التحقق إلزامي في البيانات نفسها**: القاعدة ترفض مهمة `completed` بلا `verified_at`، وخطوة `succeeded` بلا `verification.passed = true`، و`failed` بلا خطأ معلن، و`attempts > max_attempts`. هذه القيود في SQL وفي العقود معًا، ويختبر `tests/test_r202_v2_schema.py` أن الطبقتين ترفضان الحالات نفسها.

## 5. عقود API v2

- المسارات الجديدة تحت `/api/v2/*`. مسارات v1 (`/api/*`، `/civilization/*`) تبقى كما هي حتى سحبها في R-224.
- أجسام v2 هي العقود الخمسة في [`contracts/v2/`](contracts/v2/README.md): `task`، `step`، `agent_spec`، `artifact`، `message`. كلها صارمة (حقل غير معروف = خطأ)، ومطابقة لأعمدة الجداول.
- لا مسار v2 منفذ في R-202. أول المسارات تأتي مع البنود التي تحتاجها (R-204 فما بعد)، وكل مسار يُضاف إلى `API.md` في دفعته.

## 6. اسم المنتج

- الاسم **AGOS** (Agent Orchestration System). كلمة «Civilization» تُحذف من الواجهة والوثائق الحالية لأنها توحي بآلاف الوكلاء (بقية الوهم الذي أزاله R-201).
- التنفيذ في R-203 مع التنظيف (رأس الواجهة `web/src/App.jsx` واسم الحزمة `agent_civilization` يبقى اسمًا داخليًا للكود حتى يُسحب v1 في R-224 — إعادة تسمية الحزمة الآن تكسر الاستيرادات بلا فائدة للمستخدم).

## 7. البدائل المرفوضة

- **Node/TypeScript للخادم**: إعادة كتابة كل الكود الحقيقي بلا فائدة للمستخدم.
- **قاعدة منفصلة أو مخطط `public` لـv2**: الأولى تكلفة، والثانية تصادم مع جداول v1 الحية.
- **إطار وكلاء خارجي كامل (LangGraph/CrewAI) كنواة**: يربط المشروع بإطار لا نتحكم في تطوره، ويخفي الحالة خارج قاعدتنا. يمكن استخدام مكونات منها كأدوات بعد التقييم (R-214).
- **Redis أو Celery للطابور**: خدمة إضافية بتكلفة، والطابور القائم يكفي ومختبر.
- **الإبقاء على PostgREST في v2**: لا معاملات عبر عدة جداول.

## 8. العواقب والحدود

- R-202 **لا يغيّر أي سلوك حي**: لا مسار جديد، ولا تطبيق للمخطط على Supabase الحي، ولا سر جديد، ولا تكلفة.
- المخطط v2 مختبر على PostgreSQL 18 محليًا وعلى PostgreSQL 17 + pgvector في CI (job ‏`storage`)، لا على Supabase المستضافة. التطبيق الحي في R-204.
- `depends_on` مصفوفة بلا مفتاح أجنبي (Postgres لا يدعمه للمصفوفات)؛ صحة الاعتماديات مسؤولية المنسق ومختبرة في R-210.
- فهرس البحث الدلالي يُنشأ لكل نموذج تضمين في R-216 (البعد يختلف حسب النموذج).
- صلاحيات الأدوار التفصيلية (من يحذف، من يدعو) في R-204؛ R-202 يضع العزل بين المساحات فقط.

# القاعدة الحاكمة: الدفعة الذرية الواحدة

هذه السياسة أعلى أولوية من السرعة أو سهولة الدمج. لا تُجزّأ آثار التنفيذ والتوثيق إلى PRs متتابعة.

## مكونات الدفعة

| الأثر | متى يلزم |
|---|---|
| كود/إعداد/واجهة/مخطط/ترحيل | إذا تغيّر السلوك أو البنية |
| اختبار جديد أو تعديل اختبار متأثر | لكل تغيير سلوكي، مع حالة فشل تثبت أن الاختبار يكتشف المشكلة |
| `docs/governance/ROADMAP.md` | في كل دفعة، تحديث حالة المهام في نفس PR |
| `docs/governance/PROJECT_STATE.md` | في كل دفعة، الأرقام والحالة والقيود الفعلية |
| `docs/governance/CHANGELOG.md` | في كل دفعة |
| `docs/governance/QUALITY.md`, `OPERATIONS.md`, `API.md`, `DATA_MODEL.md` | حسب نوع التغيير |
| `docs/audit/` raw evidence | لكل تغيير كود أو إعداد أو اختبار مهم وفق بوابة الحوكمة |
| سجل ملفات التغيير والمخاطر | كل دفعة |

## قواعد قبول الدفعة

1. يربط وصف PR كل مهمة في الخارطة بالكود والاختبار والدليل.
2. التشغيل المرفق بالدليل يشير إلى SHA بالضبط؛ نجاح اختبار على commit مختلف لا يكفي لقبول هذا الالتزام.
3. اذكر كل `skipped`, `deselected`, `xfail`, `warning` وأسبابها؛ لا تضعها في عداد النجاح.
4. لا توسّع التغطية الظاهرية بحذف tests أو تقليل assertions أو تحويل فشل إلى skip دون ADR ومبرر وموافقة.
5. لا تغيّر حماية `main` لتجاوز فشل. الفحوص التي تتطلب أسرارًا/خدمة خارجية تُفصل كـ integration job آمنة ومعلومة.
6. لا تسجل المهمة `done` عند كتابة الكود فقط؛ لا بد من الاختبار والأدلة وتحديث الحالة والوثائق معًا.
7. إذا أُعيق اختبار بسبب غياب سر أو خدمة، الحالة `blocked` أو `conditionally accepted`، لا `done` كاملة.
8. أدلة الإنتاج والضغط لا تُستبدل بمخرجات mocks أو unit tests.

## اختبار البوابة

يجب أن يشمل اختبار governance الحالات التالية: PR تنفيذية بلا ROADMAP تفشل؛ بلا PROJECT_STATE تفشل؛ بلا CHANGELOG تفشل؛ تغيير كود بلا أدلة audit يفشل؛ تغيير API بلا وثيقة API المطلوبة يفشل؛ دفعة مكتملة مع الملفات المطلوبة تنجح. تبقى الاختبارات السلبية والايجابية محفوظة كأدلة.

# خارطة الطريق الرئيسية — إحياء AGOS والتوسع إلى 10,000 وكيل ومليون مهمة

**المرجع:** المستودع `reeveero-tech/All-hand`، الحالة المرجعية التي تمت مراجعتها: رأس `main` هو `8457ad3b1a8860b1f0985937e58796258ea84f94` عند إعداد الخطة؛ يعاد التحقق منه عند التنفيذ.  
**مهم:** هذه خطة جديدة مقترحة وليست شهادة إنجاز. مهامها لا تصبح `done` إلا مع الأدلة.

## الرؤية

ترقية النظام الحالي تدريجيًا مع الحفاظ على جميع الملفات والمجلدات، وتوحيد مسارات التنفيذ المتوازية، والتوجيه، والذاكرة، والوكلاء والأدوات، ورفع القدرة بطريقة مقاسة وقابلة للاستعادة. لا تسعى الخطة إلى تضخيم الأرقام على حساب الموثوقية.

## أهداف النجاح النهائية

1. **صيانة كاملة قابلة للتدقيق:** جرد 100% من الملفات المتعقبة؛ لكل ملف تصنيف ودور ونقاط استدعاء/استيراد واختبارات أو قرار مبرر بشأن كيفية التحقق منه. صفر حذف/نقل/إعادة تسمية غير مصرح به.
2. **تكامل وظيفي:** المسارات المعتمدة موحدة عبر عقود واضحة مع واجهات توافق للمكونات القديمة؛ لا تضارب بين مسارات `real` و`specialists` أو بين نظامي التخزين/الذاكرة.
3. **10,000 وكيل:** إنشاء 10,000 هوية/عامل منطقي موزع، واختبارات تنفيذ فعلية على عينات/مجموعات متدرجة، ثم إثبات تشغيل مكونات مختارة مع كل القيود. يجب توضيح إن كان العدد يعني وكلاء منطقيين أم عمليات/حاويات منفصلة؛ لا يلزم إنشاء عملية نظام لكل وكيل.
4. **مليون مهمة:** قبول وتتبع مليون مهمة في حالة تراكم/جدولة عبر بيئة موزعة، مع معرفات متينة، عزل المستأجرين، backpressure، إلغاء، استرداد بعد الانقطاع، وعدم فقد أو تكرار غير مضبوط. يختبر التنفيذ النشط الفعلي بأهداف متدرجة ومقاسة. مليون استدعاء LLM نشط في اللحظة نفسها هدف مختلف لا يمكن ادعاؤه بلا موارد ونموذج تكلفة منفصل.
5. **10,000 أداة فعلية:** سجل يضم 10,000 أداة قابلة للاكتشاف، مع تعريفات وعقود وإصدارات وصلاحيات واختبارات ودليل تنفيذ؛ تُعلن الأداة `certified/usable` فقط بعد اجتياز القبول. الوصول إلى الرقم على مراحل 100 → 1,000 → 10,000، ولا تُحتسب aliases أو entries المعطلة.
6. **جودة وموثوقية:** مقاييس موثقة للصحة، والدقة، والهلوسة، والالتزام بالمصادر، والأمن، والتكلفة، وزمن الاستجابة، ومعدلات الفشل؛ بوابات نشر لا تسمح بانحدار غير مبرر.
7. **قاعدة ذرية صارمة:** كل PR تنفيذي يضم الكود والاختبارات والتوثيق والأدلة وخارطة الطريق وحالة المشروع وسجل التغييرات المتأثرة في الدفعة نفسها.

## تفاصيل المهام

### P0 — الحوكمة وإدخال الخطة
- **R-151 — تكامل الخطة:** أضف الحزمة في `docs/governance/roadmaps/revival-scale/`، حدّث `ROADMAP.md` و`PROJECT_STATE.md` و`CHANGELOG.md` ودليل التدقيق في PR واحدة. حالة بقية المهام `planned`.
- **R-152 — تثبيت عدم الحذف:** أضف قائمة قبول في قالب PR أو بوابة حوكمة تحقق عدم وجود حذف/rename غير مصرح به، أو على الأقل دليل diff صريح بالملفات المحذوفة/المنقولة (المطلوب: صفر). لا تغيّر قواعد حماية الفرع الحالية في هذه المهمة.
- **R-153 — مواصفات الدفعة الذرية:** طبّق قائمة قبول على جميع PR التنفيذية: اختبارات + وثائق الحالة والخارطة وسجل التغييرات + أدلة حسب نوع التغيير. اختبر البوابة بحالات موجبة وسلبية.
- **R-154 — تعريف الحالات والادعاءات:** افصل `planned`, `in_progress`, `blocked`, `done`, `accepted`، وعرّف متى يجوز استعمال `production-ready`. أي بند بلا دليل لا يصبح منجزًا.

### P1 — الجرد وإحياء كل ملف
- **R-155 — جرد 100%:** املأ `file_inventory_template.csv` أو بديل آلي قابل للتتبع لكل الملفات المتعقبة، لا الشيفرة فقط: ملفات الإعدادات، migrations، الاختبارات، scripts، الواجهة، التوثيق، CI، وملفات البيانات. اذكر تاريخ آخر تعديل لكنه ليس قرارًا.
- **R-156 — رسم خريطة المكونات:** استخرج نقاط الدخول، الاستيرادات، استدعاءات الوحدات، التبعيات، مسارات الخادم والواجهة، عامل التنسيق، التخزين والذاكرة والاتصال بالأدوات. صنف الملفات التي لم يُعرف من يستدعيها `unresolved` بدل حذفها.
- **R-157 — تدقيق العقود والتكرار:** حدد الوظائف المكررة أو المسارات المتوازية (`real`/`specialists`، `agos_kernel`، طبقات الأدوات/الذاكرة). وحّد عبر واجهة معيارية ومحولات توافق؛ لا تحذف implementations القديمة.
- **R-158 — خط أساس لكل مكون:** نفذ import/compile/lint/schema/unit/contract tests الملائمة، وبيّن التغطية ومناطق الاختبار الغائبة. أضف smoke test لكل نقطة دخول ولكل خدمة داخلية قابلة للتشغيل.

### P2 — الرصد وعقود الخدمات
- **R-159 — مقاييس موحدة وآمنة:** أضف telemetry منضبطة للطلب والمهمة والمرحلة والوكيل والأداة والذاكرة ومزود النموذج مع `trace_id`, `task_id`, `tenant_id` المستعار/المجزأ. لا تسجل الأسرار أو نصوص prompts/results افتراضيًا.
- **R-160 — عقود الخدمات:** وثّق واختبر عقود REST/SSE والتخزين والطابور وLLM ومزودي الأدوات والذاكرة ببيانات JSON schema/contract tests، مع فشل واضح عند اختلاف العقد.
- **R-161 — صحة التكامل الحي:** أنشئ اختبارات اختيارية آمنة لـPostgreSQL/PostgREST أو Supabase ومزود LLM والأدوات الخارجية باستخدام حسابات اختبار ومفاتيح مؤقتة؛ صنف كل نتيجة كـmock/local/live ولا تخلط بينها.

### P3 — التوسع والتنسيق
- **R-162 — سجل وكيل معياري:** افصل هوية الوكيل وتخصصه عن العامل/المهمة المنفذة، وأضف registration/health/liveness/capacity/saturation، وإدارة النسخ والتوقف. اختبر 10k كتعريف منطقي خفيف دون عمليات نظام لكل وكيل.
- **R-163 — طابور مهام دائم:** صمم/حسّن طبقة طابور قابلة للتوسع مع حالة موثوقة في التخزين، claim/lease، انتهاء lease، إعادة تشغيل، جدولة عادلة، idempotency keys، ومنع duplicate side effects قدر الإمكان. أبق واجهة API المتوافقة.
- **R-164 — backpressure والحدود:** limits مستقلة لمزود النموذج والشبكة والتخزين والمحلي؛ حدود طول الطابور، معدلات القبول، مهلات، إلغاء، circuit breakers، retry jitter، DLQ، وRetry-After. إثبات أن ضغط خدمة لا يعطل الخدمات الأخرى.
- **R-165 — خطط DAG واعتمادات المراحل:** التبعيات بين المراحل، مخرجات منظمة، schema validation، موافقات قبل الأفعال الحساسة، فشل مرحلة، retry موضعي، تعويض/استئناف، مهلة كلية، وميزانية التكلفة/الوقت.
- **R-166 — تنسيق متعدد الوكلاء:** سياسة تقسيم العمل وتجميع النتائج، اختيار خبراء، منع الحلقات اللانهائية، حد أقصى للتفويض، قفل/تسليم الموارد، رسالة idempotent، واختبارات آلاف المشاركين المنطقيين ورسائل فاشلة/متأخرة/مكررة.

### P4 — الذاكرة والهلوسة والجودة
- **R-167 — توحيد طبقة التجربة والذاكرة:** عقد واحد للكتابة/الاسترجاع/التصفية والتعلم، مع توافق للواجهات القديمة؛ لا توحيدًا سطحيًا يُفقد محتوى أو بيانات. عرّف الذاكرة المؤقتة والدائمة والمتجهية/الدلالية كاستراتيجيات اختيارية مدروسة.
- **R-168 — ثبات واستعادة الذاكرة:** اختبارات عملية بعد إعادة تشغيل عملية حقيقية، وحذف/احتفاظ حسب المستأجر، ومهلات وفشل التخزين، وترحيلات نموذج البيانات، وإعادة بناء الفهارس، وحدود الحجم، والتنافس بين القراءات والكتابات.
- **R-169 — benchmark جودة/هلوسة:** مجموعة بيانات ثابتة ذات مصدر وترخيص، أسئلة لها إجابات مرجعية، أسئلة بلا معلومات كافية، حالات مصادر متعارضة، حقن تعليمات، إجابات زائفة معقولة، وعينات عربية وإنجليزية. قياس factuality/groundedness/calibration/abstention/tool correctness.
- **R-170 — بوابة جودة الناتج:** التحقق من المخرجات بواسطة schemas وأدوات حقيقية واختبارات وvalidators؛ فصل الثقة النموذجية عن الدليل، اشتراط citations للأبحاث، وتفعيل الامتناع عن الجواب عندما لا توجد أدلة كافية. قارن النتائج قبل/بعد لكل تغيير في النموذج أو التعليمات.

### P5 — هدف 10,000 أداة
- **R-171 — سجل أداة موحد:** معرف فريد، وصف دقيق، tags/قدرات، input/output JSON Schema، الإصدار، المصدر/الترخيص، الصلاحيات، أثر جانبي/read-only، idempotency، مهلة، cost/latency estimates، health، اختبار ومالك. استخدم المخطط في `specs/tool_registry_contract.schema.json` كبداية ومراجعته قبل فرضه.
- **R-172 — بوابات أمان الأدوات:** sandbox/isolated worker حيث يلزم، allowlists، credentials قصيرة الأجل، فصل أسرار المستأجرين، منع SSRF/DNS rebinding، حدود وقت/CPU/ذاكرة/مخرجات، طلب موافقة على الأفعال الخارجية أو التدميرية، وسجل تدقيق منقح.
- **R-173 — استيراد الأدوات:** محولات مُقيدة لـMCP وOpenAPI وأدوات داخلية/CLI/connectors، مع مراجعة صلاحيات كل عملية. اعتبر metadata والعلامات القادمة من مصدر خارجي غير موثوقة حتى تُراجع؛ لا تعتمد على اكتشاف أداة من الوصف وحده.
- **R-174 — توجيه الأدوات حسب المهمة:** بحث capability matching ثم ترتيب الجودة والتوفر والصلاحيات والتكلفة والزمن والخصوصية. جرّب tool call بخطة تحقق ثم تحقق من النتيجة؛ fallback إلى أداة بديلة فقط إن كان آمنًا.
- **R-175 — اعتماد 10k أدوات:** بوابة مرحلية 100 ثم 1,000 ثم 10,000 سجل أداة فريد/قابل للتنفيذ. سجل عدد discovered/registered/tested/certified/disabled منفصلًا. لا تحتسب aliases كأدوات إضافية. أي tool جديد يحتاج contract tests وsecurity review واختبار smoke قبل `certified`.

### P6 — اختبار الضغط إلى الحدود
- **R-176 — إطار حمل قابل للتكرار:** أضف ملفات k6 لقياس HTTP/arrival-rate وLocust للسيناريوهات المعتمدة إذا كان ملائمًا. ثبّت إصدارات أدوات الاختبار، وافصل workload generator عن الخدمة المقاسة، واحفظ raw logs/metrics/config/commit SHA. لا تجعل اختبار حمل مليون مع CI التقليدي افتراضيًا.
- **R-177 — اختبار كل خدمة وعامل:** لكل API/queue/store/LLM adapter/tool adapter/worker/orchestrator/memory service: baseline، load، stress، spike، soak، failure/recovery. اكتب حدودًا لكل endpoint ونوع العملية، بما فيها cancellation وSSE وlimits.
- **R-178 — سلالم 10k وكيل:** شغّل مراحل 100، 500، 1,000، 2,500، 5,000، 10,000 وكيل منطقي ثم اختبارات العمل الحقيقي بمستوى متدرج. في كل مرحلة قس startup, memory, CPU, task dispatch latency, completed/failed, queue depth, fairness, duplicates, per-specialization skew. أوقف تلقائيًا عند تجاوز حدود الأمان أو التكلفة.
- **R-179 — سلالم مليون مهمة:** 10k → 100k → 250k → 500k → 1,000,000 task records/queued/in-flight lifecycle في بيئة مخصصة. افصل `accepted`, `queued`, `claimed`, `running`, `waiting_on_provider`, `completed`, `failed`, `cancelled`. اختبر idempotent replay وrestart وqueue recovery. وثق معدل الإدخال ومعدل الإتمام لا مجرد عدد السجلات.
- **R-180 — ضغط ذاكرة وأدوات ونماذج:** اختبر memory growth، cache/index saturation، عشرات الآلاف من definitions، استرجاع tool catalog، مزود بطيء أو يرفض الطلبات، rate limits، وtimeouts. لا ترسل مليون طلب حقيقي لمزود LLM دون محاكاة/ميزانية محددة.
- **R-181 — chaos/soak/تعافي:** تعطيل عامل أو عقدة، تأخير الشبكة، خطأ التخزين، انقطاع مزود LLM، tool result غير صالح، DLQ، إعادة التشغيل، التكرار، عطل جزئي، وsoak لعدة ساعات في بيئة مُعتمدة. تحقق من عدم فقد المهام أو كشف بيانات بين المستأجرين.

### P7 — قبول النشر
- **R-182 — اختبار القبول الحي:** في بيئة staging مماثلة للإنتاج، تحقق من /health و/health/ready، auth وtenant isolation، إنشاء المهمة وتنفيذها واسترجاعها بعد restart، الذاكرة، مزود النموذج والأدوات المطلوبة، SSE، وواجهات المستخدم.
- **R-183 — runbooks والتكاليف:** وثق طريقة النشر والرجوع، secrets rotation، migrations، النسخ الاحتياطي والاستعادة، on-call، SLO/alerts، تقديرات التكلفة حسب معدلات العمل، وحدود المزود. لا تفعّل خطة سحابة مدفوعة تلقائيًا دون ميزانية معتمدة.
- **R-184 — تقرير قرار الجاهزية:** تقرير `GO / CONDITIONAL GO / NO-GO` مدعوم بالأدلة والأرقام والفجوات المفتوحة. `GO` يتطلب نجاح كل البوابات الحرجة، وعدم وجود مشكلة أمنية حرجة، وإثبات السعة المستهدفة في بيئتها المحددة. لا يكفي نجاح CI وحده.

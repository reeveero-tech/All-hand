# R-149 (Security QA): مصفوفة تغطية الأمن واختبارات الانحدار

> تجرد تغطية الأمن كما طلبت مهمة R-149: كل ضمان مربوط بالاختبار الذي يثبته **فعليًا** — بالـassertions الحاسمة لا بأسماء الاختبارات — مع حدود الإثبات، ثم الفجوات المثبتة التي أغلقتها هذه الدفعة والعيبان اللذان اكتُشفا وأُصلحا. الفئات مرتبطة بمتطلبات مهمة R-149 (تقرير التدقيق الخارجي الأصلي لم يُعثر عليه في المستودع — لم تُنسب إليه صفوف). خط الأساس: main بعد PR #155 (`d224652`)؛ الفرع `m7/r149-security-qa-regression-matrix`. الأدلة: السجلات `270`–`275`.

## الفجوات المثبتة — أُغلقت في هذه الدفعة

الملف `tests/test_r149_security_qa_gaps.py` (19 اختبارًا). كل الحقن عبر **الطبقة الحقيقية** (`SupabaseStorage`) ضد PostgREST وهمي محلي قابل للتحكم عبر HTTP فعلي (أحكام لكل (طريقة، جدول): رمز رفض، قطع النقل قبل الرد، رد جزئي يُقطع أثناء قراءة الجسم، إبطاء يتجاوز مهلة العميل المقرّرة، وتمييز **بالحمولة**)، ومسجّلة منفصلة: نتيجة التنفيذ وحالة `TASKS`، الحمولات المُحاوَلة (نسخ عميقة)، ما حُفظ فعلًا، الأحداث المنشورة، وإحصاءات الطبقة.

- **G1 — فشل كتابة التخزين داخل `/api/chat` والمسار الخلفي**: كل الكتابات مرفوضة (401) ← الاستجابة 200 بعقدها الكامل وبالنتيجة الحقيقية، والذاكرة بالحالة الصحيحة، والكتابات الأربع مُحاوَلة لا مُتخطاة، ولا ادعاء حفظ في الاستجابة؛ رفض الإدراج وحده (403) ← التحديث النهائي مُحاوَل بالحالة الصحيحة؛ رفض التحديث النهائي وحده (بعد قبول الإدراج وrunning) ← الصف الدائم يبقى متأخرًا ولا يُدّعى نجاحًا محفوظًا؛ رفض الحدث النهائي وحده (بعد قبول حدث الإنشاء)؛ قطع النقل (قبل الرد، ورد جزئي أثناء القراءة)؛ مهلة نقل حتمية (مهلة العميل 0.2ث وخلفية تنام 1ث) — بلا انتظار حي. نتيجتا ok=True وok=False كلتاهما مغطاتان.
- **G2 — فشل قراءة المهمة المخزنة** (`GET /api/tasks/{id}` غائبة عن الذاكرة): 404 بنص ثابت (العقد المتدهور الحالي: فشل القراءة لا يتميز عن غياب الصف) مع تسجيل **كل محاولة** بمعاملات استعلامها — كلها تحمل `task_id` ونطاق المستأجر، ولا محاولة بلا مرشح المستأجر (لا بديل غير مقيّد)؛ وللمستأجر الآخر: محاولاته بنطاقه فقط والصف لا يظهر.
- **G3 — عدم التسريب عبر مسارات الخطأ**: علامة سرية تمر فعلًا عبر جسم رفض الخلفية ← لا تصل الاستجابات/النتائج/الأحداث (مثبت)؛ عبر استثناء داخلي في وكيل حقيقي ← تصل قناة نتيجة الخطأ الموثقة فقط (لا الأحداث ولا السجلات)؛ عبر استثناء تحت طبقة التخزين ← الاستجابات نظيفة والإحصاءات تحفظ نوع الاستثناء فقط، والنص الخام يصل سجل المشغل فقط (نصوص استثناءات النقل لا تحمل مفاتيح بطبيعتها — المفتاح يسافر في العناوين).
- **G4 — استثناء داخل وكيل حقيقي**: `execute()` الحقيقي بلا تعديل، والمعالج الذي يستدعيه يرفع (خارج مزدوج مخالف للعقد) — المهمة تنتهي **failed** بنتيجة تحمل الخطأ وحدث صادق، لا تبقى معلقة. (ملاحظة منهجية: وكيل يخالف عقد execute نفسه بالرفع خارج معالجات الوكلاء الحقيقيين الثلاثة — خارج نطاق هذا العقد؛ عقد الوكلاء يضمن عدم الرفع وهو ما يثبته هذا الاختبار عند حدوده.)

## العيبان المكتشفان والمُصلحان (أصغر إصلاح)

الفشل قبل الإصلاح محفوظ بالسجل `270` (اختباران فاشلان + 11 ناجحًا، RC=1)، وبعده `271` (320 ناجحًا، RC=0):

1. **محوّل الوكيل الخارجي يعكس جسم خطأ الخلفية إلى المستأجر**: `RuntimeError(f"HTTP {status}: {body[:300]}")` كان يجعل أول 300 حرف من جسم رد الخلفية نص خطأ التنفيذ — الذي يصبح نتيجة المهمة المرئية للمستأجر عبر `GET /api/tasks/{id}` وسطر السجل. خلفية معادية تردد مفتاح المحوّل الإداري (المُرسل في `Authorization`) في جسم الخطأ كانت توصله للمستأجر — مثبت تجريبيًا قبل الإصلاح («KEY IN TENANT-VISIBLE RESULT: True»). الإصلاح: السبب صار `HTTP <status>` فقط؛ أسباب رفض SEC-01/SEC-05 الثابتة بلا تغيير (كل اختباراتها ناجحة).
2. **سطر رفض التخزين يسجل جسم الخلفية خامًا**: `_accepted` كان يسجّل `(op, status, body[:300])` — جسم الرفض نص غير موثوق قد يردد مفتاح الخدمة؛ مثبت قبل الإصلاح (العلامة في السجل). الإصلاح: السجل يحتفظ بالعملية والرمز فقط (تشخيص RISK-013 يبقى كافيًا)؛ الإحصاءات لم تتغير (كانت تحفظ الرمز فقط أصلًا).
